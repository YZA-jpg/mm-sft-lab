**一、长输出让推理成本明显增加。**早期 Transformers 测试用 1024/2048 上限时，已经出现过 embodied 回答重复推演；48 条试跑中有 3 条截断。本轮改用单卡 vLLM、并发 4，最初不传输出上限时，个别请求超过 13 万 token 仍未结束；之后统一设置 max_tokens=65536。最新回传记录中，SIUO/MSSBench 有效生成 500/2461，其中 46 条 length，占 9.2%；仅按这些触顶回答的额度就约 301 万输出 token。部分正文反复“寻找微波炉—给出动作计划—重新确认—再次规划”。这是静态图文生成，文字里的动作不会真正执行，也没有新图像反馈。

四个长回答会占满四个并发位，所以日志的完成数可能长时间不变。此前两次相隔约 27 秒的快照中，四条各增加 497 tokens，说明那一段仍在生成；600 秒设置是无新数据等待阈值，持续返回流式数据时不会按总耗时 600 秒结束。更早的短输出预算使这类回答更早被截断；目前没有严格对照能证明重复是 vLLM 引起的。

**二、今天发现全量实际上已因准备异常退出。**本轮为 SIUO 167×3=501、MSSBench chat 1200、embodied 760，共 2461 次目标生成。最近一次状态是成功 500、准备失败 1、尚未尝试 1960；主进程已退出。最后完成时间为北京时间 10 月 23 日 01:07，12:07 检查时已无新结果约 11 小时。因此这段等待不能计作有效推理时间；后台运行也不能避免程序因异常主动退出。

失败 ID 为 mssbench/chat/0031/0/b#g0。本地对同源输入复现：原图存在、校验正常且能以 WebP 打开，但请求代码用系统 MIME 表推断格式时得到 None，拼接 data URI 时产生 TypeError。这个错误发生在发给模型之前，不能靠网络重试解决，也不是模型拒答。当前快照共有 5 张 WebP，已补兼容处理并通过全部 2127 个原始请求的离线构造验证；恢复入口保留旧结果并核对成功请求哈希。服务器尚未回传这一行 error 原文，所以仍需预检确认服务器也是同一错误，不能把本地复现直接当成服务器确诊。

**三、judge 缺失要与上述生成异常区分。**本轮退出时 judge 还没开始，DeepSeek 调用数为 0，这次耗时不来自判分。历史测试中另遇过平台图片审核拦截、图片大小限制、401 和标签解析失败。护栏不重试、按缺失报告；网络问题自动重试 5 次，即最多 6 次传输尝试。其他非护栏失败不能一概叫“DeepSeek 拒答”：格式、鉴权、输入限制等要分别记录原因，对可恢复项修复/补判，最终残留仍列数量与覆盖率；补判针对同一份已生成回答，不增加目标模型采样次数。目前程序不是所有非护栏失败都已自动重试，这部分需按分类处理完善。

## 1. 为什么以前似乎没有

| 阶段 | 可核对设置/观察 | 能得出的结论 |
| --- | --- | --- |
| 早期 HF greedy smoke | 1024 新 token，12 条中 3 条截断 | 较早阶段已经有输出触顶 |
| HF sampling 长度对照 | 1024→2048；同一 embodied 回答仍触顶并重复推演 | 增加预算没有消除该样本的重复行为 |
| HF sampling 48 条 | 2048 上限、batch 1；3/48 截断，均为 embodied | 小样本也已有问题；不能据此外推全量率 |
| vLLM 7 条 smoke | 7 条均正常 stop | 只证明这七次成功，未覆盖后续全部样本/格式 |
| vLLM 21 条 64k smoke | MSSBench 12 条中 1 条 length，所回传样本 65536 tokens、约 20 分 26 秒 | 64k 上限生效，但仍有重复规划 |
| vLLM 64k 本轮全量最近记录 | 有效 500，46 length；另 1 条准备错误后退出 | 长输出成本与异常停机均存在，尚无全量评分 |

2048 到 65536 的输出预算为 32 倍，1024 到 65536 为 64 倍；这是预算比值，不代表所有请求耗时都按相同比例放大。旧测试中既有 greedy，也有显式采样及按 ID 派生 seed；本轮接口省略采样参数和 seed，且后端、并发和覆盖样本变化。不能凭目前记录认定 vLLM 导致模型安全或能力下降。严格归因需要同输入、同预算、同解码与可比运行条件的独立对照。

## 3. 每个数据集的计时要求

| 项目 | 记录口径 |
| --- | --- |
| 冻结身份 | 模型/adapter、数据及选择、代码、生成预算、实际默认采样、trial、并发、依赖/GPU/判分服务身份 |
| 生成阶段 | benchmark 与必要子模块的开始/结束、有效/失败/未尝试数、全部请求及重试耗时、token、length、吞吐 |
| 判分阶段 | DeepSeek/WildGuard 分别记录时间、尝试量、拒答/护栏/格式错误及有效覆盖；MMStar 本地评分不伪造 LLM 时间 |
| 模型加载 | 每次服务 startup 单列；共享一次加载不按数据集重复计入 |
| 故障与恢复 | 失败请求和失败启动单列；保留各会话，重启间停机空档不当作生成时间 |
| 并发解释 | 旧诊断轮跨 benchmark 的区间会重叠，不能当独立耗时；正式轮已决定按数据集依次测试，内部继续并发；请求延迟总和仍不等于总墙钟 |

对当前混合调度记录可导出 benchmark 的会话内观测跨度、请求活动区间并集、延迟总和与每次 HTTP/退避成本；这些不是各数据集单独运行的速度。MSSBench chat/embodied 分开列。原 pipeline 失败缺少 completed 事件时，已完成 pipeline 时间会漏掉失败会话；导出器单列未闭合会话，生成阶段原有 completed 会话和逐请求成本仍保存。

新增 scripts/export_eval_v2_timing.py，只读原 run，写新 timing-snapshot 目录：dataset-timing.csv、dataset-timing.json、README.md。可用于已中断或仍在写入的 run；只读取完整日志行，不修复/截断日志、不改旧配置、不加载模型或调用 API。实际服务器数据集耗时尚未导入本地，本文不编造这些数值。

该导出器提取现有 generation、deepseek、wildguard 日志；它不会凭空补出尚未记录的本地评分耗时。正式轮须为 MMStar 等本地抽取/评分另行记录后处理时间，具体调度及计时补充在要求确认后实施。

实现事实：现有 HTTP 自动重试覆盖超时、连接问题、429/部分可恢复 HTTP 状态和 5xx；格式解析失败、鉴权、输入限制不会靠该机制自动补齐。补判应保持相同原始回答 hash，不应为补 judge 标签而重新生成目标回答。网络重试耗尽、格式、鉴权、输入限制等分别汇报，不一概归到护栏。本文记录目标要求与当前实现差距，没有宣称这些分支已全部改成自动补判。

其他既定规则继续保留：WildJailbreak 用本地 WildGuard，MMStar 不用 LLM judge；FigStep 采用用户给定 AdaShield 二分类模板；目标长度上限终止的回答保留并单列截断率；本轮不新增训练数据重叠检查。其余 benchmark 适配细节按当前版本记录，先跑通 baseline，若学长指定不同口径再显式版本化。

## 5. 确认后的正式重跑

保留旧 HF、旧 B0、无上限、64k smoke 和这次部分全量日志作为诊断。按确认结果建立新的正式配置与运行目录，从头生成，不回填旧回答；之后 baseline 与各 SFT 模型都使用同一协议。先完成全部输入格式/请求体的离线预检及覆盖各模块/图片格式的小样本生成和 judge 验收，再由用户后台启动正式全量。

最终每个模型/benchmark 同时交付：指标 x/y 与覆盖率、有效/失败/未尝试、拒判/护栏/格式错误率、截断率、生成和 judge 时间、输出 token 与吞吐、启动/失败成本、运行身份。当前文档只是确认材料，不含正式安全分数。没有向学长发送任何消息。
